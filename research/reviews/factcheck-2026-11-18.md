# ケーススタディのスライド（49 枚）とガイドの更新（14 枚）のファクトチェック（2026-11-18）

作成とは別の担当 3 人（生成 AI のサブエージェント）が、観点を分けて点検した。CS＝ケーススタディのスライド、G＝ガイドのスライド。反映の結果は末尾の表に記録する。

## 観点 1：実験結果との照合（誤り 1・不正確 6・補足 7）

1. 誤り：CS S2・S49「ガイド（149 枚）」→ 152 枚（README も同じ。README は修正済み）
2. 不正確：G S137 見出し「名前・型・位置の変化は捕まる」→ employee_id の数値化は壊れた 5 つ中 3 つしか検出されない
3. 不正確：G S44・S149 ノート、G S58 列見出し「入口の正規化で 0 件」→ B9 を直したのは overage_resolve。「入口の正規化（Cognito の client_id）と groups 超過の解決（ディレクトリ参照）で 0 件」
4. 不正確：G S149 の社内業務システムの重点（aud・ID トークン流用防止・属性の鮮度）→ aud と typ は基準。重点は normalize_gw・header_strip・freshness・overage_resolve。A の「tid の照合」は tenant_iss_bind
5. 不正確：CS S44 ノート「採用と条件付き採用を足して 57 行」→「必須・採用・条件付き採用を足して」。「7〜14%」→「約 7〜14%」
6. 不正確：CS S38 ノートの summary.md の回数の食い違いの文 → summary.md は修正済みなので削除
7. 不正確：G S36・S81・S131、CS S32「宛先を mcp-tools→orders に付け替えられた」→「mcp-tools に optional scope として割り当てた aud-orders を要求すると、元のトークンに無い orders 宛て（aud＝orders・account）が 200 で出た」
8. 補足：CS S15 の構成 BE−data_tenant_check−rls_local では A6 も通り A4 も誤処理、を注記
9. 補足：CS S23 の費用は freshness の実装そのものではなく近い操作の費用、と注記
10. 補足：CS S19 Keycloak の at+jwt はクライアント設定 access.token.header.type.rfc9068 による
11. 補足：CS S33「古さの上限 300 秒」は設定値からの推論
12. 補足：G S108「active は aud のクライアントだけ」は 3 クライアントで 1 回試した結果
13. 補足：G S149「効果と費用はケーススタディで測る」に「送信者制約の効果は未検証」
14. 補足：G S58 ノートに「Keycloak 以外は公式文書の形の模擬」

## 観点 2：標準と製品（誤り 1・不正確 5・補足 7）

1. 不正確：CS S19（S18・S5）Okta の typ application/okta-internal-at+jwt は org 認可サーバーの AT で、Okta 以外が検証すべきでない（Okta「Validate Access Tokens」）。自社 API 向けはカスタム認可サーバーの AT を模擬した、と書く。typ の値そのものは公式文書で未確認
2. 不正確：CS S19・S20・S22、G S44・S58「Cognito の AT には aud が無い」→「リソースバインディングを使わない既定では aud が無く client_id で宛先を表す（模擬はこの既定の形）」
3. 誤り：CS S29 authorization_details の `"locations": ["inv-1"]` → RFC 9396 §2.2 で locations は RS の URI。個別の資源は `identifier`
4. 不正確：CS S19 Auth0 の at+jwt → 既定は Auth0 プロファイルで typ JWT。RFC 9068 プロファイルを選んだ場合を模擬
5. 不正確：G S36「全クレームが要るならトークン交換で変換」→ Keycloak の文書では、軽量 AT で消したクレームはイントロスペクションで取得する
6. 不正確：CS S19 Keycloak の at+jwt は既定ではなく設定（観点 1 の 10 と同じ）
7. 補足：G S44・S58・S149 ノートに Entra・Cognito が模擬であることを明記
8. 補足：CS S33、G S106・S36「リフレッシュトークンが入れ替わった」→ Revoke Refresh Token を有効にしたレルムで
9. 補足：CS S33・S23、G S108 の introspection の aud 確認は Keycloak の文書に明記された仕様（互換オプションで無効化可）と添える
10. 補足：CS S32、G S127・S81 の交換で宛先が増える挙動は Keycloak の文書にある。対策の client policy executor（downscope-assertion-grant-enforcer）と、audience パラメータは絞り込み専用であることを添える
11. 補足：CS S34 organization クレームは既定で配列、マッパーの設定でオブジェクトになる
12. 補足：CS S34 Full Scope Allowed は非推奨（将来削除）
13. 補足：G S131「転送：ホップごとに交換｜MCP 仕様」→ MCP 仕様が求めるのはパススルーの禁止まで。ホップごとの交換は組織の選択

## 観点 3：論理・一貫性・読者（誤り 1・不正確 9・補足 6）

1. 誤り：CS S2・S49 のガイドの枚数（観点 1 の 1）
2. 不正確：「B」が構成（共通の基準）と題材 B（社内業務システム）の両方 → 構成を「素朴（N）／基準（B）／基準＋重点（BE）」と読み、題材は「題材 A〜C」と書き分ける
3. 不正確：共通の基準と重点がガイド S149 と一致しない（ログの規則、B の重点、C の重点）→ ガイド S149 をケーススタディの要素名に揃え、ログの規則は「基準だがケーススタディでは測っていない」と書く
4. 不正確：見送りの「失うこと」が S46 の A・C、S16・S30 本文に無い。判定ごとの書く規則が S43・S44 で揺れる → S46 を「見送るもの／失うこと／見直し条件／検証 ID」に、規則は一覧表の読み方の文に揃える
5. 不正確：S47 の限界に、題材 C の重点は模擬の STS 上の確認（Keycloak の標準交換では act が出ない）、9 つの受け手は典型の再現実装、ワークロード ID は前提、点検は生成 AI の担当、を足す
6. 不正確：S30・S46 の深さの見直し条件 →「委任の深さ・縮小を規定する標準（WG 草案以上）が出たら」
7. 不正確：S29 の承認の要素名がガイド S125 と違う。承認は CIBA でなく記録の参照で代用 → 揃えるか、違いを明記
8. 不正確：S10 サブタイトル → immutable_id は B13、namespace は A5 が通り、題材 B では正規の B21 を誤拒否
9. 不正確：S33・S34 のタイトルを「Keycloak 26.8 では」に限定。Cognito は「resource を指定しない場合」
10. 不正確：ガイドの Part の参照先（S2 の Part 12、S9 の Part 0、S44 の Part 9）
11. 補足：S15・S3 のタイトルが本文より強い
12. 補足：S27・S28 の C9 を止めた仕組み（期限切れか取り消しの再確認か）を明記
13. 補足：S37 の「0」はモデルの定義による。S38 のノート（観点 1 の 6）
14. 補足：初出の用語（N・B・BE、BOLA、AT、PDP、MCP、act、RAR、cnf.jkt、ID-JAG、p50・p95）、overage_resolve の初出、S44 の「必須 16 行」と 9 要素の対応、ガイド S7（用語）への誘導
15. 補足：S46・S48 から行動に移しにくい（観測する指標、担当・順番・終わりの基準、run_all.py への誘導）
16. 補足：言い回しのずれ（exp のずれ 30 秒とガイドの「数分まで」、ロールと groups、agent:expense と agent:expense-assistant）

## 一覧表への波及

- HDR-01：Okta の照合値を「カスタム認可サーバーの AT（org 認可サーバーの AT は Okta 以外が検証しない）」に。Auth0 は RFC 9068 プロファイル選択時、Keycloak は設定による、を明記
- authorization_details.locations と identifier の判定（題材 C）を RFC 9396 §2.2 に合わせる
