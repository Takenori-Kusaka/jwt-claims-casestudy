# 判定の方針（ケース A・B・C）

この一覧表の判定は、ケーススタディの実験環境（`cs/`）とガイド（https://github.com/Takenori-Kusaka/jwt-claims-guide）の前提での結論で、2026-11-17 時点のもの。どの組織にもそのまま当てはまる答えではない。

## 共通の前提（3 ケースとも）

- 外部の IdP（Entra ID・Keycloak・Auth0・Okta・Cognito）のトークンは、入口（ゲートウェイ）でだけ検証し、組織の内部トークンに交換する。内側のサービスが読むのは内部トークンだけ。
- したがって、IdP 固有のクレーム（ベンダー独自の行）は「入口での入力としてだけ使い、内部トークンには載せない」。判定は原則「不採用・代替あり」で、代替は組織のクレーム（下の ORG 行）か標準のクレーム。入口の正規化で読む必要があるものは、条件に「入口の正規化でのみ読む」と書く。
- 共通の基準（どのケースでも必須）：`iss`、`sub`、`aud`、`exp`、`iat`、`jti`、ヘッダーの `typ`（at+jwt）、組織の名前空間オブジェクト `https://claims.example.com/` の中の `tenant_id`（社内システムでは固定値 corp）と `user_id`。必須のクレームが欠けたら拒否、型を固定、トークン全文と個人情報のクレームはログに残さない。
- 個人情報のクレーム（氏名・メール・電話・住所・生年月日など）は、アクセストークンには載せない（必要なら UserInfo か API で取る）。ID トークンでの扱いは、そのケースのクライアントがログイン画面で使う場合だけ「条件付き採用（ID トークンのみ）」。
- 変わりやすい細かい権限・関係（オブジェクトごとの許可、文書の共有先など）はトークンに載せず、PDP・DB で都度判定する（ガイド Part 4・5）。
- 草案のクレームは「条件付き採用」までとし、見直し条件に「RFC になったら」などを書く。
- 用途が違う領域のクレーム（SIP/PASSporT、端末の証明 EAT、CI/CD のワークロード属性、3GPP など）は、ケースに関係しなければ「対象外」。ただし CI/CD の属性は、ケース B でデプロイ基盤を扱わないので対象外、と理由を書く。

## 組織の独自クレーム（本ケーススタディで定義。ORG 行として表に加える）

名前空間オブジェクト `https://claims.example.com/` の中に置く。書き手は入口のトークン発行サービスだけ。

## ケースごとの重点（実験環境の要素と対応）

- **A マルチテナント SaaS**：テナントと発行者の照合（tenant_iss_bind）、データ側のテナント照合、SET LOCAL と行単位の制御、テナント単位の鍵。細かい権限のトークン化は見送り（PDP で都度）。
- **B 社内業務システム**：入口での正規化、ヘッダーの除去、重要な操作の鮮度確認、groups 超過の解決。送信者制約（DPoP・mTLS）と JWE は見送り（見直し条件：トークンが社外・取引先へ渡るとき、または盗用の兆候）。
- **C AI エージェントの委任**：act の連鎖を正しく読む、宛先に束縛した交換（転送しない）、承認の束縛（authorization_details）、タスク単位の短命トークン、深さの組織規則（3 段）。標準による深さの強制は、標準がないため見送り。

## 判定の値

必須（共通基準）／採用／条件付き採用／不採用・代替あり／不採用・不要／不採用・禁止／対象外

- 採用・条件付き採用：「どういう場合に使うか」を書く。
- 不採用・代替あり：代替クレームの ID を必ず書き、その代替が同じケースで採用・必須になっていること。
- 不採用・不要：そのケースでは使い道がない。
- 不採用・禁止：載せると害がある（例：アクセストークンに個人情報、本人が書き換えられる属性での認可）。
- 不採用の理由には「それで何ができなくなるか」を書く。不採用と条件付き採用には見直し条件を書く。
