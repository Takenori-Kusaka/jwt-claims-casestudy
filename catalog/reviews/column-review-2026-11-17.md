# クレーム一覧表の列設計レビュー（2026-11-17）

作成者とは別の担当が、列の案をレビューした記録。根拠に開いた一次資料：RFC 7643 §2.2・§7（SCIM の属性の特性）、RFC 7519 §10.1.1（IANA 登録の雛形）、NIST IR 8112 §3.1・§3.2。SP 800-162、SP 800-63C-4、OWASP ASVS 5.0 は調査メモ 05 の節番号つきの要約を参照。

## 結論

最初の案は「どこに定義されているか」は書けるが、テックリーダーが判断に使う 4 点（誰が値を書けるか、値がいつ変わるか、認可に使ってよいか、個人情報とログの扱い）が書けない。ケース別の判定も、理由・代替・条件が 1 つの欄に混ざり、絞り込めない。

## 用語の統一（利用者の指示を反映した改訂版）

列名と値では「クレーム」だけを使う。「属性」は、SCIM・eduPerson・inetOrgPerson・NIST のように、クレームの元になるディレクトリの属性を指すときに限って本文で使う（読み方のシートで宣言する）。

| 最初の案 | 直した名前 | 理由 |
|---|---|---|
| 属性（分類） | 分類 | 「属性」はクレームの訳語と紛らわしい |
| 対応する属性（代替の No） | 代替クレーム（No）。ケースごとの列 | どちらがどちらを代替するか、どのケースの話かも曖昧 |
| 名前 | クレーム名 | 入れ子は「.」区切りの経路で書く |
| 目的 | 意味（表すこと／表さないこと） | 分類の「同意・目的」や purpose というクレームと紛れる |
| 型 | 値の型 | トークンの型と区別する |
| 規格（出典） | 出典と出典の節 | ベンダーの文書も入るので「規格」は不正確 |
| サービス | IdP での扱い | GitHub Actions などのプラットフォームと区別する |
| 確認済み | 確認日 | いつの情報かを示す |

## 直した列

- 「独自か」は出典の種別とほぼ重なるため、値の語彙と出典の種別で表す。
- IdP ごとの対応（5 列）は概念ごとの性質なので、同義グループの単位でも引けるようにする。ID トークンとアクセストークンで扱いが違う場合は分けて書く。プラットフォームが発行する行には「対象外」を使う。
- 「載るトークン」の「両方」は曖昧なので、具体的なトークンの種類を並べる。
- 「対応する属性」は「代替クレーム（ID）」とし、ケースごとの列に置く。「属性」は「クレーム」の訳語と紛らわしいため、表の中では「クレーム」に統一する（列名「分類」も同じ理由）。
- 並べ替えで崩れない ID（CLM-0001 など）を No とは別に持つ。

## ケースごとの判定列（A・B・C 共通の形）

| 列 | 規則 |
|---|---|
| 判定 | 必須（共通基準）／採用／条件付き採用／不採用・代替あり／不採用・不要／不採用・禁止／対象外 |
| 条件 | 条件付き採用のときだけ必須 |
| 代替クレーム（ID） | 不採用・代替ありのときだけ必須 |
| 用途／失うこと | 採用なら「いつ使うか」、不採用なら「何ができなくなるか」 |
| 見直し条件 | 不採用と条件付き採用で必須 |
| 検証 ID | ケーススタディの検証の ID |

整合の確認（条件付き書式）：代替ありなのに代替 ID が空、代替先が同じケースで採用されていない、条件付きなのに条件が空。空白の区切り列は置かない（フィルタが切れるため）。

## 誤読のリスクと対策

- 「IdP で既定」は「認可に使ってよい」ではない → 「認可に使ってよいか」を判定の近くに置く。
- 「標準」は「IdP 間で同じ意味」ではない（groups を名前で返す IdP と ID で返す IdP がある）。
- 不採用は禁止ではない → 「不要」と「禁止」を値で分ける。
- 判定はケーススタディの前提での結論で、日付時点のもの。
- 行数はクレームの数ではない（出典ごとの行）。数えるなら同義グループで。
- 個人情報のクレームの「採用」は、アクセストークンに載せてよいと読まれやすい → 載るトークンと個人情報の区分を並べる。
- 未確認の行と草案の行は、見た目で区別する。
