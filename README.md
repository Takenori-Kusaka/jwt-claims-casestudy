# JWT クレーム設計ケーススタディ（実験基盤）

「JWT クレーム設計ガイド」の対になる実測です。どの組織でも外せない**共通の基準**が何を防ぎ、題材ごとの**重点**が何を足し、**見送り**が何を残すかを、攻撃と正規の要求、大きさ、遅延、反映までの時間、変更で壊れる受け手の数で測ります。LLM は使わず、同じ手順で何度でも同じ判定になります（時刻は仮想の時計で進めます）。

## 構成

| 記号 | 名前 | 中身 |
| --- | --- | --- |
| N | 素朴（よくある誤り） | ヘッダーの alg に従う、kid をパスに使う、jku/jwk を信じる、aud・exp・typ を見ない、テナントをヘッダーから取る、接続プールでセッション単位の SET、受け手ごとに IdP 別の読み方、groups が無ければ制限なし、委任のトークンをそのまま上流へ |
| B | 共通の基準 | alg の許可リスト、設定済みの鍵だけ、iss の完全一致、aud に自分、exp 必須（ずれ 30 秒）、typ、組織の名前空間と型の固定、不変の ID、必須クレームが欠けたら拒否、トークン全文をログに残さない |
| BE | 共通の基準＋重点 | A：テナントを発行者（レルム）と照合、SET LOCAL と行単位の制御（RLS）。B：入口で IdP ごとに検証して内部トークンに交換、受け手は内部トークンだけを読む、重要な判断は属性とセッションを引き直す、groups の超過はディレクトリで解決。C：ホップごとの交換と act の連鎖、今の行為者（最も外側の act）で認可、承認は authorization_details で照合、タスク単位 300 秒、交換時に取り消しを再確認、深さ 3 の組織規則 |

## 題材

- **A マルチテナント SaaS**：Keycloak のレルム t1・t2、Postgres の行単位の制御。テナントの出どころ、BOLA、接続プールの文脈の残り、他テナントの管理者がマッパーで tenant_id を偽る攻撃。
- **B 社内業務システム**：Keycloak のレルム corp と、Entra ID・Okta・Cognito の形を再現した模擬の発行元。ID トークンの流用、宛先の差し替え、ヘッダーの偽装（アンダースコア版を含む）、groups の超過、異動後の古い属性、ログアウト後のトークン、Okta のログイン名の再利用、Cognito の aud なしトークン、盗まれたトークンの再送。
- **C AI エージェントの委任**：内部のトークン発行サービス（模擬）、MCP 風のツールサーバー、上流の請求書 API。パススルー、代理の混乱、act の読み違い、承認の照合と偽造、委任の取り消し、委任の深さ。
- **汎用の攻撃（Part 1）**：alg none、RS256→HS256、kid の注入、jku、jwk、exp なし、期限切れ、宛先違い、別の発行者、typ、必須クレームの欠落、型の揺れ。

各ケースの狙いと、ガイドのどの Part を確かめるかは [results/summary.md](results/summary.md) の表にあります。

## 実行

前提：Windows から WSL（Ubuntu-24.04）の Docker が使えること。Keycloak 26.8.0 と Postgres 16 のイメージを使います（メモリは約 0.8 GB）。

```bash
python -m venv .venv && .venv/Scripts/python -m pip install "pyjwt[crypto]==2.10.1" jwcrypto "psycopg[binary]" requests
.venv/Scripts/python run_all.py        # コンテナを起動 → 全題材を実行 → results/ に書き出し → コンテナを停止
```

結果：`results/matrix.json`（構成 × ケース）、`results/scores.json`、`results/measurements.json`（大きさ・遅延・反映の時間・変更の影響・行数）、`results/summary.md`。

## 注意

- 鍵（`keys/`）、パスワード、クライアントシークレットはすべて試験用です。
- 素朴な検証器（N）は、過去にライブラリやアプリが実際にしていた誤りを手で再現したものです。現在の PyJWT はこのうちいくつかを拒否します。
- 模擬の IdP は、2026 年 11 月時点の公式文書にある形を再現したもので、実際のサービスの挙動のすべてではありません。
